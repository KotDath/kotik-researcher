# Proposal: project-workspaces-pi-chats

## Зачем

Закладываем фундамент агентной системы для исследователей: desktop-приложение,
в котором пользователь открывает/создаёт директории проектов и ведёт внутри них
LLM-чаты — полноценные сессии pi agent со встроенными tools (файлы, shell),
скоупированные на директорию проекта. Это первая фича приложения: сейчас в
`src/` только каркас Electron, собственного поведения нет.

## Что меняется

- Проекты: открытие существующей директории (системный диалог), создание новой
  (родительская папка + имя → mkdir, без git init и шаблонов), список недавних
  проектов (JSON в Electron userData, переживает перезапуск), пометка
  недоступных (удалена/перемещена), «убрать из списка» для любого проекта —
  директория на диске не трогается. Одновременно открыт один проект.
- Чаты: внутри проекта — сессии pi (полный agent со всеми tools). Список чатов
  по дате активности, новый чат (всегда чистая сессия), переименование,
  удаление (в корзину ОС), поиск/фильтр по имени. В пустом проекте первый чат
  создаётся автоматически. Отправка сообщений со стримингом ответа; tool-вызовы
  — сворачиваемыми блоками. Ошибки стриминга — карточкой в ленте с retry, ввод
  не блокируется; чат без настроенных ключей отправку не блокирует. Генерация
  продолжается в фоне при навигации по чатам и при переключении проекта.
- Настройки: экран настроек — API-ключи и base-url провайдеров, модель по
  умолчанию; ключи в safeStorage Electron; набор провайдеров не ограничивается
  (дефолтный multi-provider pi), фокус проверки — OpenAI-compatible (включая
  локальные). Приложение автономно от установленного pi CLI: каталог данных pi
  переопределяется в собственное расположение, пользовательский `~/.pi` не
  читается.
- Интеграция: pi SDK (`@earendil-works/pi-coding-agent@0.82.1`, версия
  зафиксирована точно) встраивается в main-процесс Electron; RPC-подпроцесс —
  неприемлем для Electron. Нативный риск `photon-node` снимается спайком
  первым шагом фичи (блокер): упакованная сборка + один ответ от LLM на Linux,
  верификация prebuilds под macOS/Windows. При провале — чинить упаковку; при
  «грязном» решении — отдельное решение о переезде на Tauri с RPC-sidecar,
  фича блокируется до него.

## Capabilities

- Новые: `project-workspaces` — проекты как директории: открытие/создание,
  список недавних, недоступные проекты, один проект за раз.
- Новые: `pi-chat-sessions` — чаты-сессии pi внутри проекта: список, создание,
  переименование, удаление, поиск, стриминг с tool-блоками, ошибки и фоновая
  генерация.
- Новые: `llm-provider-settings` — автономная конфигурация провайдеров LLM:
  ключи в safeStorage, base-url, модель по умолчанию, изоляция от `~/.pi`.
- Изменённые: нет (`specs/capabilities/` пуст — первая фича приложения).

## Влияние

- **Сборка main-процесса переводится на ESM** (SDK — ESM-only, `type: module`,
  node >= 22.19; Electron 43 в проекте подходит с запасом). Меняется конфиг
  electron-vite и точка входа.
- **Новые зависимости:** `@earendil-works/pi-coding-agent@0.82.1` (точная
  фиксация, обновления — осознанным решением) и упаковщик (electron-builder) —
  в проекте его нет, а критерий приёмки требует упакованный артефакт.
- **Главный риск:** нативная зависимость `@silvia-odwyer/photon-node` (Rust/
  N-API, не optional) в упакованном Electron — снимается спайком-блокером до
  начала UI-работ. Подробности и митигации — в design.md, фактура —
  research/2026-07-28-pi-sdk.md.
- **Безопасность:** агент выполняет tools (bash, файлы) с правами приложения в
  директории проекта — осознанно принято (модель pi без пермишенов).
- **design.md нужен:** кросс-резовые решения — ESM-миграция сборки, проброс
  ключей (setRuntimeApiKey vs authPath), IPC-контракт main↔renderer, lifecycle
  AgentSessionRuntime, стратегия упаковки нативного модуля.
