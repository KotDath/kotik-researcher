# Delta: pi-chat-sessions

## Purpose

Внутри открытого проекта пользователь ведёт LLM-чаты — сессии pi agent с
полным набором встроенных tools (файлы, shell и т.д.), скоупированные на
директорию проекта. Capability покрывает управление списком чатов, отправку
сообщений со стримингом ответа, отображение tool-вызовов, обработку ошибок и
фоновую генерацию при навигации.

## ADDED Requirements

### Requirement: Агент полного профиля в директории проекта

В каждом чате система ДОЛЖНА запускать полный pi agent со всеми встроенными
tools (файловые операции, shell и т.д.) — без отключения или фильтрации tools.
Рабочей директорией агента ДОЛЖНА быть директория активного проекта.

#### Scenario: Агент работает со встроенными tools в скоупе проекта

- **GIVEN** открыт проект с директорией `/home/user/proj`
- **WHEN** пользователь отправляет сообщение, требующее файловых операций
- **THEN** агент выполняет tool-вызовы (файлы, shell) с рабочей директорией
  `/home/user/proj`

### Requirement: Список чатов проекта

Система ДОЛЖНА отображать список чатов активного проекта, отсортированный по
дате последней активности (свежие первыми). Источником списка ДОЛЖНО быть
хранилище сессий pi, скоупированное по директории проекта.

#### Scenario: Список чатов отсортирован по активности

- **GIVEN** в проекте есть чаты с разной датой последней активности
- **WHEN** пользователь открывает проект
- **THEN** список чатов показывает чаты проекта, свежие первыми
- **AND** чаты других проектов в список не входят

#### Scenario: История чата читается после перезапуска

- **GIVEN** пользователь вёл диалог в чате и перезапустил приложение
- **WHEN** пользователь открывает тот же проект и чат
- **THEN** история сообщений чата отображается полностью
- **AND** диалог можно продолжить

### Requirement: Автоматическое создание первого чата

При открытии проекта без чатов система ДОЛЖНА автоматически создавать первый
чат, чтобы пользователь мог сразу писать.

#### Scenario: Открытие пустого проекта

- **GIVEN** в проекте нет ни одного чата
- **WHEN** проект открывается (созданием или из списка недавних)
- **THEN** автоматически создаётся новый чат и становится активным

### Requirement: Создание нового чата

Система ДОЛЖНА позволять создать новый чат в активном проекте. Новый чат —
всегда чистая сессия pi (без контекста других чатов). Fork существующей сессии
НЕ входит в данный change.

#### Scenario: Новый чат — чистая сессия

- **GIVEN** в проекте есть чат с историей
- **WHEN** пользователь создаёт новый чат
- **THEN** создаётся пустой чат без сообщений
- **AND** он становится активным

### Requirement: Переименование чата

Система ДОЛЖНА позволять переименовать чат; новое имя ДОЛЖНО сохраняться в
хранилище сессий pi и отображаться в списке чатов, переживая перезапуск
приложения.

#### Scenario: Переименование сохраняется

- **WHEN** пользователь переименовывает чат в «Анализ конкурентов»
- **THEN** в списке чатов отображается имя «Анализ конкурентов»
- **AND** после перезапуска приложения имя сохраняется

### Requirement: Удаление чата

Система ДОЛЖНА позволять удалить чат. Удаление ДОЛЖНО выполняться перемещением
файла сессии в корзину ОС (восстановимо); если корзина недоступна в ОС —
допускается безвозвратное удаление. Удалённый чат исчезает из списка. Удаление
активного чата ДОЛЖНО переводить пользователя в другой чат проекта или, если
чатов не осталось, запускать автоматическое создание первого чата.

#### Scenario: Удаление чата в корзину

- **GIVEN** в проекте два чата, активен первый
- **WHEN** пользователь удаляет первый чат
- **THEN** файл сессии перемещается в корзину ОС
- **AND** чат исчезает из списка, активным становится оставшийся чат

#### Scenario: Удаление последнего чата проекта

- **WHEN** пользователь удаляет единственный чат проекта
- **THEN** чат удаляется и автоматически создаётся новый пустой чат

### Requirement: Поиск чатов по имени

Система ДОЛЖНА позволять фильтровать список чатов проекта по подстроке имени.

#### Scenario: Фильтрация по подстроке

- **GIVEN** в проекте есть чаты «Анализ рынка» и «Черновик статьи»
- **WHEN** пользователь вводит в поиск «анализ»
- **THEN** в списке остаётся только чат «Анализ рынка»

### Requirement: Отправка сообщений со стримингом ответа

Система ДОЛЖНА отправлять сообщения пользователя агенту и отображать ответ
потоком по мере генерации (текст появляется инкрементально, без ожидания
полного ответа).

#### Scenario: Стриминг ответа

- **WHEN** пользователь отправляет сообщение в чат
- **THEN** ответ агента появляется в ленте инкрементально по мере генерации
- **AND** по завершении генерации ответ остаётся в истории чата

### Requirement: Tool-вызовы сворачиваемыми блоками

Система ДОЛЖНА отображать tool-вызовы агента (файлы, shell и т.д.) в ленте чата
между сообщениями в виде сворачиваемых блоков. В блоке ДОЛЖНО быть видно, какой
tool вызван, и статус выполнения (выполняется/завершён).

#### Scenario: Блок tool-вызова в ленте

- **WHEN** агент во время ответа выполняет tool-вызов
- **THEN** в ленте чата появляется сворачиваемый блок с именем tool и статусом
  выполнения
- **AND** блок можно развернуть, чтобы увидеть детали вызова

### Requirement: Ошибка стриминга карточкой с retry

При ошибке во время стриминга (сеть, невалидный ключ, rate limit, обрыв)
система ДОЛЖНА показывать в ленте чата карточку ошибки с текстом причины и
кнопкой «повторить». Ввод сообщений НЕ ДОЛЖЕН блокироваться ни во время
генерации, ни после ошибки.

#### Scenario: Карточка ошибки и повторная отправка

- **WHEN** во время генерации ответа происходит ошибка провайдера
- **THEN** в ленте чата появляется карточка с текстом причины и кнопкой
  «повторить»
- **AND** поле ввода остаётся доступным
- **AND** нажатие «повторить» инициирует повторную попытку получения ответа

### Requirement: Чат без настроенных ключей не блокируется

Система ДОЛЖНА разрешать отправку сообщений даже если API-ключи провайдера не
настроены. Ошибка провайдера ДОЛЖНА приходить карточкой ошибки в чат (см.
требование «Ошибка стриминга карточкой с retry»), а не блокирующим экраном.

#### Scenario: Отправка без ключей

- **GIVEN** ни один API-ключ не настроен
- **WHEN** пользователь отправляет сообщение
- **THEN** сообщение отправляется, и в ленте появляется карточка ошибки
  провайдера с возможностью повторить
- **AND** поле ввода остаётся доступным

### Requirement: Фоновая генерация при навигации

Переключение чата или проекта во время генерации НЕ ДОЛЖНО прерывать её:
генерация продолжается в фоне, ответ дозаписывается в сессию на диске. При
возврате в чат пользователь ДОЛЖЕН видеть готовый или дозаписывающийся ответ
(стриминг возобновляется в UI с актуальной позиции).

#### Scenario: Возврат в чат с фоновой генерацией

- **GIVEN** в чате X идёт генерация ответа
- **WHEN** пользователь переключается на другой чат, а затем возвращается в X
- **THEN** ответ в чате X продолжает отображаться с актуальной позиции (или
  уже готов)
- **AND** никакая часть ответа не потеряна

#### Scenario: Переключение проекта во время генерации

- **GIVEN** в проекте A идёт генерация ответа
- **WHEN** пользователь переключается на проект B, а затем возвращается в A
- **THEN** генерация в проекте A завершилась в фоне, ответ полностью
  дозаписан в сессию

### Requirement: Работа в упакованном приложении

Все поведения данной capability ДОЛЖНЫ работать в упакованной (packaged)
сборке приложения на целевых платформах: Linux, macOS, Windows. В частности,
pi SDK со своей нативной зависимостью ДОЛЖЕН создавать сессию и получать ответ
от LLM в упакованной сборке.

#### Scenario: Спайк — ответ LLM в упакованной сборке

- **WHEN** приложение собрано и упаковано для Linux
- **THEN** в упакованном приложении pi SDK создаёт сессию и получает ответ от
  LLM (включая загрузку нативного модуля photon-node)

#### Scenario: Наличие нативных prebuilds под целевые платформы

- **WHEN** выполняется проверка сборки
- **THEN** подтверждено наличие prebuilds нативной зависимости photon-node
  под Linux, macOS и Windows
