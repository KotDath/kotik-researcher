# Vision: project-workspaces-pi-chats

> Статус: финализировано (интервью завершено, пользователь подтвердил полноту).
> Фактура по pi-sdk: [research/2026-07-28-pi-sdk.md](../../../research/2026-07-28-pi-sdk.md).

## Цель и границы

**Цель:** фундамент будущей агентной системы для исследователей — desktop-приложение,
в котором пользователь открывает/создаёт директории проектов и ведёт внутри них
LLM-чаты (сессии pi) с полноценным агентом.

**Модель pi в чате:** полный pi agent со всеми встроенными tools (файлы, shell и т.д.),
скоуп — директория проекта. Ничего не отключаем.

**Параллельность:** одновременно открыт только один проект. Переключение — через
список недавних проектов. Один AgentSessionRuntime в памяти.

**Модель проекта:** проект = директория на диске. Сейчас метаданные минимальны
(путь, дата последнего открытия), но модель не должна блокировать добавление
метаданных в будущем (имя, описание, настройки) — пользователь явно ожидает
«возможные будущие метаданные».

**Входит в MVP (все пункты подтверждены):**
1. Открыть существующую директорию (системный диалог).
2. Создать новую директорию проекта из приложения.
3. Список недавних проектов для быстрого переключения.
4. Список чатов (сессий pi) текущего проекта + создание нового чата.
5. Отправка сообщений со стримингом ответа в UI.

**НЕ входит (за границей MVP):**
- Несколько проектов одновременно (вкладки/окна проектов).
- Отключение/настройка tools per-чат.
- Собственные агентные возможности поверх pi (это следующие фичи).

## Техническая реализация

**Форма интеграции (из research, не оспорена):** pi SDK (`@earendil-works/pi-coding-agent`)
в main-процессе Electron, один AgentSessionRuntime на открытый проект. RPC-подпроцесс —
запасной вариант. Версия пакета зафиксирована точно: 0.82.1 (последняя на момент
интервью); обновления — осознанным решением, не автоматически.

**Провайдеры LLM:** приложение не должно искусственно ограничивать набор провайдеров —
используем дефолтную multi-provider конфигурацию pi (всё, что он поддерживает из
коробки). Фокус пользователя — OpenAI-compatible endpoints (включая локальные:
Ollama, LM Studio, self-hosted) — на них проверяем в первую очередь.

**Автономность от установленного pi (жёсткое требование):** приложение НЕ полагается
на то, что у пользователя уже установлен pi CLI или настроен ~/.pi. Конфигурация
(провайдеры, ключи, модель) управляется самим приложением; каталог данных pi
переопределяется в собственное расположение приложения (SDK это позволяет), а не
читается из пользовательского ~/.pi. Ключи вводятся в приложении.

**Список недавних проектов:** JSON-файл в Electron userData (пути + дата последнего
открытия). Переживает перезапуск (урок LRN-20260728-001: состояние на диске).
Сами сессии чатов хранит pi на диске, скоупированные по директории проекта.

**Создание нового проекта:** выбор родительской папки + ввод имени → просто mkdir.
Без git init, без шаблонов.

## UI/UX

**Layout:** классика — слева sidebar (имя проекта, список чатов, «новый чат»,
«сменить проект»), справа активный чат со стримингом ответа.

**Новый чат:** всегда чистая сессия pi (newSession). Fork — за границей MVP.

**Операции с чатами (всё входит в MVP):**
- список чатов проекта (по дате последней активности);
- переименование (SDK: appendSessionInfo);
- удаление (SDK не умеет — удаляем jsonl-файл сессии через файловую систему);
- поиск/фильтр по именам чатов.

**Действия агента в UI:** tool-вызовы (файлы, shell и т.д.) показываются
сворачиваемыми блоками между сообщениями — что вызвано и статус выполнения.

**Настройки:** отдельный экран настроек — API-ключи и base-url провайдеров,
модель по умолчанию. Ключи хранятся в safeStorage Electron. Настройки доступны
в любой момент (не обязательный мастер при первом запуске — это не оговаривалось,
но экран настроек выбран как основной механизм).

## Риски и опасения

**Главный технический риск (из research):** нативная зависимость pi SDK
`@silvia-odwyer/photon-node` (Rust/N-API, обработка изображений, не optional) —
работа в упакованном Electron не подтверждена: prebuilds под все платформы не
верифицированы, electron-builder может не скопировать `.node`-файл.

**Архитектурное ограничение от пользователя (жёсткое):** решение, завязанное на
RPC-подпроцесс поверх Electron, неприемлемо — пользователь заявил, что в таком
случае предпочтёт сменить фреймворк на Tauri. Уточнение из раунда 5: нюанс именно
в сочетании — RPC внутри Electron не нужен; при переезде на Tauri RPC-sidecar
становится приемлемым («если получается грязно — обсуждаем переезд на tauri с rpc»).
Следствие: SDK-в-main-процессе Electron — основной и единственный путь MVP.

**Стратегия по риску photon-node (подтверждена):**
1. **Спайк первым шагом фичи**, до реализации UI: упакованное приложение + pi SDK
   создаёт сессию и получает один ответ от LLM. Успех = ответ получен в
   упакованной сборке.
2. При провале — **чинить упаковку** (asarUnpack, явное копирование `.node`,
   пересборка модуля).
3. Если чинится только «грязно» — **выносим переезд на Tauri (с RPC-sidecar)
   отдельным решением**, фича блокируется до него.

**Целевые платформы MVP:** Linux, macOS, Windows (все три) — спайк и проверка
prebuilds photon-node должны покрывать все три ОС (как минимум верификация
наличия prebuilds под macOS/Windows).

**Прочие риски:**
- pi 0.x, API меняется каждые 1–7 дней → версия зафиксирована (0.82.1), обновления осознанно.
- Удаление чатов обходом SDK (через ФС) — теоретический риск рассинхрона, если pi
  поменяет формат хранения; при фиксированной версии контролируемо.

## Компромиссы (что выбрано важнее и почему)

- **Автономность приложения > совместимость с пользовательским ~/.pi:** приложение
  не разделяет конфиг с установленным pi CLI — предсказуемость и self-contained
  важнее шаринга сессий/логинов с CLI.
- **Стабильность > свежесть pi:** точная фиксация 0.82.1, обновления — осознанное
  решение, а не автоматика.
- **SDK в процессе > изоляция процессов:** RPC-подпроцесс дал бы изоляцию, но ценой
  внешней зависимости — отвергнуто пользователем (вплоть до готовности сменить
  фреймворк).
- **Простота модели > параллельность:** один проект за раз, без вкладок — меньше
  состояния, быстрее MVP.

## Крайние случаи и failure modes

- **Директория проекта удалена/перемещена вне приложения:** в списке недавних проект
  помечается «недоступен»; при попытке открыть — понятное сообщение + кнопка
  «убрать из списка».
- **Переключение чата/проекта во время стриминга:** генерация продолжается в фоне,
  pi дозаписывает ответ в сессию на диске; при возврате в чат виден
  готовый/дописывающийся ответ. Ничего не теряется.
- **Проект без чатов:** при открытии автоматически создаётся первый чат —
  пользователь может сразу писать.
- **Ошибка во время стриминга** (сеть, невалидный ключ, rate limit, обрыв):
  карточка ошибки в ленте чата с текстом причины и кнопкой «повторить».
  Ввод не блокируется.
- **Чат без настроенных ключей:** отправка разрешена; ошибка провайдера придёт
  карточкой в чат (пользователь выбрал «разрешаем, ошибка по факту» — блокирующий
  ввод отклонён).

## Критерии приёмки

E2E-сценарий с перезапуском (подтверждён пользователем):
1. Создать проект (новая директория) из приложения.
2. Открыть чат (создаётся автоматически) и отправить сообщение.
3. Увидеть стримящийся ответ агента со сворачиваемыми tool-блоками.
4. Перезапустить приложение.
5. Проект в списке недавних, чат на месте, история читается, можно продолжить диалог.
