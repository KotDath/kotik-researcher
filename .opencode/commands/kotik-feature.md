Пользователь хочет новую фичу:

> $ARGUMENTS

## Preflight-гейты (при провале — НЕ начинать, скажи что чинить)

1. `git status` — дерево чистое. Грязное → «сначала разберитесь с
   незакоммиченными изменениями, иначе реализация смешается с чужими
   правками». Пользователь может явно разрешить продолжить.
2. Нет другого change со `Status: draft` в specs/changes/. Есть → уточни
   через question tool: продолжаем его или создаём новый.
3. Грепни docs/LESSONS.md по теме фичи (ключевые слова из запроса) —
   релевантные уроки учитывай при сборе требований и включи в бриф
   spec-writer'у.

## Стадия «спека»

1. Если описание расплывчато — задай уточняющие вопросы через question tool.
   Цель: понять желаемое поведение, границы (что НЕ входит) и ограничения.
2. Если для спеки не хватает фактуры о внешних библиотеках/подходах —
   делегируй researcher исследование, дождись отчёта.
3. Делегируй spec-writer создание change. Бриф: дословные требования
   пользователя, что отвергнуто, выводы из research (путь к отчёту),
   релевантные уроки из LESSONS.md, имя change в kebab-case.
4. Покажи пользователю итог: proposal, список требований по дельтам,
   количество задач. Скажи явно: «правьте текстом или примите через
   /kotik-approve».

Не переходи к реализации до одобрения пользователя.
