# Research: pi-sdk — программное управление сессиями pi для Electron-приложения

**Дата:** 2026-07-28

## Вопрос

Фича в SDD-цикле: desktop-приложение (Electron + electron-vite + React 19), в
котором пользователь открывает/создаёт директории проектов, а внутри проекта
создаёт и переключается между LLM-чатами — сессиями pi. Нужно выяснить:

1. Что такое «pi-sdk» — точные npm-имена, репозиторий, версии, лицензия,
   зрелость.
2. Позволяет ли pi программно управлять сессиями (создавать, перечислять,
   возобновлять, переключаться) вне его TUI.
3. Как pi хранит сессии на диске и есть ли скоупинг по директории проекта.
4. Форма интеграции в Electron: SDK в main-процессе vs CLI-подпроцесс (RPC).
5. Какие UI-возможности реалистичны: список сессий, возобновление,
   переименование, удаление, стриминг в собственный UI.

Результат информирует vision-интервью и спеку фичи.

## Находки

### 1. Идентификация: дизамбигуация «pi-sdk»

«pi-sdk» как отдельного npm-пакета не существует. Это SDK, встроенный в экосистему
pi — AI agent harness, изначально созданный Mario Zechner (badlogic). С 2026 года
проект переехал: репозиторий `badlogic/pi-mono` → **`earendil-works/pi`** (Earendil Inc.),
пакеты `@mariozechner/*` → **`@earendil-works/*`** (старые помечены deprecated:
«please use @earendil-works/pi-coding-agent instead going forward»).

Наиболее вероятная трактовка запроса пользователя подтверждена: «pi» — это pi
coding agent (CLI `pi`), а его «сессии» — сохранённые JSONL-разговоры, которыми
можно управлять программно.

Актуальные пакеты (все версии 0.82.1, MIT, репозиторий github.com/earendil-works/pi):

| Пакет | Назначение |
|---|---|
| `@earendil-works/pi-coding-agent` | CLI + **SDK целиком** (`createAgentSession`, `SessionManager`, `ModelRuntime`, …) |
| `@earendil-works/pi-ai` | Унифицированный multi-provider LLM API (типы сообщений, `getModel`) |
| `@earendil-works/pi-agent-core` | Agent runtime: tool calling, state management |
| `@earendil-works/pi-tui` | Терминальный UI (нужен только для InteractiveMode) |

Зрелость и активность: проект живой и очень активный — релизы каждые 1–7 дней,
последний 0.82.1 вышел 2026-07-25 (за 3 дня до исследования). Репозиторий: 79.5k
звёзд, 5137 коммитов, сайт pi.dev с полной документацией. Версии 0.x — API ещё
эволюционирует (например, `AgentSessionRuntime` появился недавно как слой над
`AgentSession`), к обновлениям нужно относиться внимательно.

### 2. Программный API управления сессиями

SDK официально поддерживает встраивание: документация «SDK — embed pi in Node.js
applications», раздел Programmatic Usage на pi.dev.

Ключевые сущности (всё экспортируется из `@earendil-works/pi-coding-agent`):

```typescript
import {
  createAgentSession, createAgentSessionRuntime, createAgentSessionServices,
  createAgentSessionFromServices, ModelRuntime, SessionManager, SettingsManager,
  DefaultResourceLoader, getAgentDir,
} from "@earendil-works/pi-coding-agent";
```

**Создание/открытие сессий (SessionManager):**

```typescript
SessionManager.inMemory(cwd?)              // без персистентности
SessionManager.create(cwd, sessionDir?)    // новая персистентная сессия
SessionManager.continueRecent(cwd)         // продолжить последнюю
SessionManager.open("/path/to/session.jsonl")  // открыть конкретный файл
SessionManager.forkFrom(sourcePath, targetCwd) // форк из другого проекта

// Листинг — статические методы, скоуп по cwd:
await SessionManager.list(cwd)     // сессии конкретной директории
await SessionManager.listAll(cwd)  // все сессии всех проектов
```

**Сессия (AgentSession):**

```typescript
const modelRuntime = await ModelRuntime.create();
const { session } = await createAgentSession({
  cwd: "/path/to/project",                       // рабочая директория
  sessionManager: SessionManager.create(cwd),
  modelRuntime,
});

await session.prompt("текст", options?);         // отправка, резолвится по завершении
session.subscribe((event) => { ... });           // стриминг-события
session.steer(text); session.followUp(text);     // очередь сообщений во время стриминга
session.setModel(model); session.abort(); session.dispose();
session.sessionFile; session.sessionId; session.messages; session.isStreaming;
```

**Переключение сессий в живом процессе (AgentSessionRuntime)** — именно то, что
нужно для фичи «переключение между чатами»:

```typescript
const runtime = await createAgentSessionRuntime(createRuntime, {
  cwd, agentDir: getAgentDir(),
  sessionManager: SessionManager.create(cwd),
});

await runtime.newSession();                       // новая сессия
await runtime.switchSession("/path/to/s.jsonl");  // переключиться на сохранённую
await runtime.fork(entryId);                      // форк от сообщения
await runtime.importFromJsonl();                  // импорт
// ВАЖНО: runtime.session заменяется; подписки на события надо переоформлять
```

**Стриминг-события** (`session.subscribe`): `message_update` (с
`assistantMessageEvent.type === "text_delta" | "thinking_delta" | ...`),
`tool_execution_start/update/end`, `agent_start/end`, `turn_start/end`,
`queue_update`, `compaction_start/end`, `auto_retry_*` — достаточно для полноценного
собственного чат-UI с индикацией tool-вызовов.

### 3. Персистентность и скоупинг по проекту

Подтверждено документацией Session File Format:

```
~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl
```

- `<path>` — cwd с `/`, заменёнными на `-`. То есть **скоупинг по директории
  проекта встроен нативно**: сессии проекта X лежат в своей поддиректории,
  `SessionManager.list(cwd)` возвращает только её сессии.
- Формат: JSONL, первая строка — `SessionHeader` (`{type:"session", version:3,
  id, timestamp, cwd}`), далее записи типов `message`, `model_change`,
  `thinking_level_change`, `compaction`, `branch_summary`, `label`,
  `session_info`, `custom`, `custom_message`. Записи образуют **дерево** через
  `id`/`parentId` (branching из коробки, `/tree` в TUI).
- Версия формата: v3 (v1/v2 автомигрируются при загрузке).
- Дополнительно: `SessionManager.create(cwd, sessionDir?)` и CLI-флаг
  `--session-dir <path>` позволяют переопределить каталог хранения — можно
  хранить сессии приложения отдельно от CLI-сессий пользователя.

**Переименование:** есть нативно — `SessionManager.appendSessionInfo(name)`,
запись `session_info` в JSONL; имя показывается в листинге вместо первого
сообщения. В RPC — команда `set_session_name`.

**Удаление:** API удаления в SessionManager нет — сессии удаляются удалением
`.jsonl`-файлов (TUI использует `trash` CLI, если доступен). Для приложения это
просто `fs.unlink`/`shell.trashItem` Electron.

### 4. Встраивание в Electron main

Технические факты по пакету `@earendil-works/pi-coding-agent@0.82.1`:

- **ESM-only**: `type: "module"`, `exports` содержит только `import` (нет
  `require`). В Electron main ESM поддерживается с Electron 28; в electron-vite
  main-процесс можно собирать в ESM (build.rollupOptions / `type: "module"`).
  CJS-require не сработает.
- **engines: node >= 22.19.0**. Сопоставление с Electron:
  - Electron 38 → Node 22.18 (формально ниже требования);
  - Electron 39 → Node 22.20 (подходит);
  - **в проекте уже electron ^43.2.0** — подходит с запасом.
- **Нативная зависимость**: `@silvia-odwyer/photon-node@0.3.4` (обработка
  изображений, Rust/N-API) — в `dependencies`, не optional. N-API-модули
  ABI-стабильны и обычно работают в Electron без пересборки, но: (а) факт
  наличия prebuilds под все целевые платформы **не подтверждён**; (б) при
  упаковке через electron-builder может понадобиться явное копирование `.node`.
  Это главный технический риск — проверить на этапе прототипа.
- **Зависимости**: `undici`, `cross-spawn`, `glob`, `jiti`, `chalk`, `typebox` и
  др. + внутренние `@earendil-works/pi-{ai,agent-core,tui}` — pi-tui тянется
  транзитивно, но без терминала не активируется, если не запускать
  `InteractiveMode`.
- **Аутентификация** (`ModelRuntime.create()`): приоритет — runtime override
  (`setRuntimeApiKey`, не персистится) → `~/.pi/agent/auth.json` (создаётся с
  правами 0600) → env-переменные (`ANTHROPIC_API_KEY` и т.д.) → custom keys из
  `models.json`. Можно указать свои пути: `ModelRuntime.create({ authPath,
  modelsPath })` или in-memory credential store.
- **Провайдеры** (по документации Providers): OAuth-подписки — ChatGPT Plus/Pro
  (Codex), Claude Pro/Max, GitHub Copilot, xAI, OpenRouter, Radius; API-ключи —
  Anthropic, OpenAI, Google Gemini, DeepSeek, Mistral, Groq, Cerebras, xAI,
  OpenRouter, Vercel AI Gateway, Hugging Face, Fireworks, Together, Kimi,
  MiniMax, Qwen, Xiaomi MiMo и др.; облачные — Azure OpenAI, Amazon Bedrock,
  Google Vertex, Cloudflare; локальные — llama.cpp, Ollama/LM Studio/vLLM через
  custom models. Пользователь может один раз залогиниться через CLI `pi
  /login` — и приложение разделит его `auth.json`.

**Альтернатива — RPC-подпроцесс**: `pi --mode rpc` — JSON-протокол поверх
stdin/stdout (команды `prompt`, `new_session`, `switch_session`, `fork`,
`set_session_name`, `get_state`, `get_entries`, `get_tree`…; события стриминга —
те же). Сами авторы рекомендуют: для Node.js-приложения — SDK напрямую; RPC —
для других языков и когда нужна изоляция процесса.

### 5. Ограничения и подводные камни

- Сессии **не привязаны к TUI** — вся механика сессий (создание, листинг,
  возобновление, переключение, дерево) доступна через SDK/RPC. Исходный страх
  «сессии только внутри TUI» не подтвердился.
- `AgentSessionRuntime`: после `newSession()/switchSession()/fork()` объект
  `runtime.session` заменяется — нужно перевешивать `subscribe()` (и
  `bindExtensions()` при использовании расширений). Это явно описано в доке;
  архитектура приложения должна это учитывать.
- Версии 0.x: быстрая эволюция API (30+ минорных релизов за май–июль 2026).
  Фиксировать версию и читать changelog при обновлении.
- Удаление сессий — только через файловую систему (нет SDK-метода).
- `photon-node` — нативный модуль (см. выше), риск при упаковке.
- ESM-only — конфигурация electron-vite для main должна быть ESM.
- Права: у pi нет своей системы пермишенов — агент выполняет bash/edit с
  правами процесса, т.е. приложения. В UI это надо учитывать (доверие к
  проектной директории — отдельная тема, у pi есть docs/security).

## Сравнение: SDK-in-main vs CLI-подпроцесс (RPC)

| Критерий | SDK в main-процессе | RPC-подпроцесс (`pi --mode rpc`) |
|---|---|---|
| Рекомендация авторов | Да, для Node.js-приложений | Для других языков / изоляции |
| Типобезопасность | Полная (TypeScript-типы событий, сообщений) | Нет (JSON по проводу, типы вручную; есть `rpc-client.ts` в исходниках как референс) |
| Управление сессиями | Полное: `SessionManager.*`, `runtime.switchSession`, листинг по cwd | Полное: команды `new_session`, `switch_session`, `set_session_name`; но **листинга сессий в RPC нет** — список придётся читать из FS или через SDK |
| Стриминг в собственный UI | `session.subscribe` → IPC в renderer | stdout JSONL → тот же IPC |
| Изоляция сбоев | Крах агента = крах main-процесса | Крах подпроцесса переживаемо |
| Зависимости приложения | +SDK и его дерево (вкл. нативный photon-node) | Пользователь должен установить CLI отдельно, либо бандлим его |
| Версия Node | Требование engines попадает в приложение (Electron 39+/43 — ок) | Не важна (свой процесс) |
| Доступ к agent state | Прямой (`session.agent.state`) | Только через команды `get_state`/`get_messages` |

## Рекомендация

**VERDICT: ставить `@earendil-works/pi-coding-agent` (0.82.1, зафиксировать
версию) и встраивать SDK в main-процесс Electron; RPC — запасной вариант.**
Уверенность: **высокая**.

Обоснование:

1. Все требования фичи покрываются нативным SDK-API: сессии скоупятся по cwd
   автоматически (`SessionManager.list(cwd)` — ровно «чаты проекта»),
   создание (`create`/`newSession`), переключение (`switchSession`),
   возобновление (`open`/`continueRecent`), переименование
   (`appendSessionInfo`), стриминг (`subscribe` + text_delta). TUI не требуется
   вообще.
2. Авторы явно рекомендуют SDK (а не RPC) для Node.js-приложений; типы событий
   и сообщений идут из коробки — меньше слой сериализации между main и
   агентом.
3. У пользователя уже Electron 43 (Node ≥ 22.20) — требование engines
   удовлетворено; ESM-only решается конфигурацией electron-vite.
4. Архитектурно: один `AgentSessionRuntime` на открытую проектную директорию в
   main-процессе; UI (React) общается через IPC; список чатов =
   `SessionManager.list(projectPath)`; удаление = trash `.jsonl`.

Что могло бы изменить рекомендацию: если при прототипировании нативный
`photon-node` не заведётся в упакованном Electron или SDK окажется нестабилен в
долгоживущем main-процессе — тогда RPC-подпроцесс (изоляция + поставка CLI
рядом с приложением), с чтением списка сессий из `~/.pi/agent/sessions/` или
через отдельный node-скрипт с SDK.

Открытые вопросы для vision-интервью / прототипа:

- Проверить `photon-node` в сборке (помечено «не подтверждено»).
- Использовать общий `~/.pi/agent` (шаринг с CLI-логином пользователя) или
  изолированный agentDir приложения (`ModelRuntime.create({authPath})`,
  `SessionManager.create(cwd, sessionDir)`) — вопрос для интервью.
- Нужна ли поддержка дерева сессий (branching) в UI v1 или достаточно линейных
  чатов.
