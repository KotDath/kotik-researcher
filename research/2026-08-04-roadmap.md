# Roadmap kotik-researcher: план работ по drafts/

Статус: зафиксированный план
Дата: 2026-08-04
Источники: `drafts/01..07`, текущее состояние репозитория (capabilities
`project-workspaces`, `pi-chat-sessions`, `llm-provider-settings`, активный
change `ui-verification-infra`)

Этот документ фиксирует план превращения текущей базы (чат на Pi SDK с
проектами и настройками провайдеров) в целевую систему из `drafts/`: зрелую
local-first исследовательскую среду с версионированным research state,
knowledge graph, воспроизводимыми экспериментами и self-improvement.

План опирается на `drafts/07-feature-backlog.md` (карточки KR-001…KR-086,
этапы A–I, срезы R0–R7) и сопоставляет его с тем, что уже реализовано.

### Ключевые расхождения с drafts

1. **Хранилище.** Сейчас проекты — JSON-файлы (`src/main/json-file.ts`).
   Drafts закрепляют рабочую гипотезу: SQLite canonical/event store +
   content-addressed artifacts + Git-backed история человекочитаемых файлов.
   Это миграция основания, и её дешевле провести сейчас, пока state мал.
2. **UI.** Сейчас одиночный чат (Sidebar + ChatArea + Settings). Целевой
   workspace — трёхпанельный: Project navigator / Content canvas / Agent panel
   с вкладками и deep links.
3. **Доменного слоя нет.** Весь research loop (brief → discovery → screening →
   evidence → claims → synthesis) ещё не начат.

## 1. Принципы плана

- **Вертикальные срезы, а не горизонтальные слои.** Каждая волна даёт
  наблюдаемый пользовательский результат, а не «подготовку инфраструктуры».
- **Сначала основание, потом research loop.** Слой данных (SQLite, event log,
  artifact store) — фундамент всего research state; строить домен поверх
  JSON-файлов, а потом мигрировать, — двойная работа.
- **Открытые решения закрываются ADR/spike до зависимых карточек**
  (список — `drafts/07` §7), а не случайным выбором библиотеки внутри задачи.
- **Каждая карточка — отдельный SDD change** через `/kotik-feature`.
  Кандидаты на `Implementation: deep`: KR-003/004 (миграции, identity,
  idempotency), KR-021 (state machine с resumability), KR-030 (схема знаний),
  KR-036 (propagation retractions), KR-051 (branches), KR-073/074 (replay,
  policy registry).
- **CS test case** (utility-based forgetting для long-horizon LLM-агентов,
  `drafts/06` §10.1) — regression-сценарий начиная со среза R2: каждый этап
  проверяется на нём end-to-end.

## 3. Волна 1 — фундамент данных (этап A, срез R0)

Цель: проект перестаёт быть набором JSON-файлов и становится
воспроизводимым версионированным состоянием — основой research state.

### ADR/spike перед кодом

1. **SQLite-библиотека и слой доступа** (открытое решение №3): better-sqlite3
   vs node:sqlite vs ORM; стратегия миграций; расположение БД внутри project
   directory.
2. **Формат domain commands/events** (открытое решение №5): схема событий
   (actor, timestamp, causation/correlation ID, schema version), idempotency
   keys, cadence снапшотов.

### Карточки (в порядке зависимостей)

- **KR-003 SQLite + миграции.** Встроенная БД внутри проекта, транзакции,
  последовательные миграции, backup перед несовместимой миграцией, атомарность
  при падении посередине. Включает миграцию существующих JSON-проектов.
- **KR-004 Типизированный event log.** Append-only события всех значимых
  изменений; повтор команды с тем же idempotency key не создаёт дубль. Это
  будущая основа episodic memory, timeline и trajectories.
- **KR-005 Artifact store.** Content-addressed хранение документов, текста,
  изображений, кода и результатов: дедупликация по hash, ссылки по hash,
  безопасное удаление. Фундамент для PDF-импорта (KR-025) и экспериментов
  (этап E).
- **KR-006 Snapshot + диагностический экспорт.** Согласованный снапшот
  доменного состояния, открываемый после перезапуска; обезличенный экспорт без
  секретов и закрытых документов.

Результат волны: срез **R0 (часть данных)** — проект хранится канонично,
события и артефакты имеют provenance, снапшот восстанавливается.

## 4. Волна 2 — workspace и управляемый агент (этап B, R0/R1)

Цель: UI из «чатика» превращается в трёхпанельный research workspace, а агент
становится управляемым (tools, permissions, видимый прогресс, остановка).

- **KR-010 Трёхпанельный workspace.** Navigator слева, content canvas в
  центре, agent panel справа; resize/collapse, сохранение layout, chat-first
  onboarding в пустом проекте. Переработка текущего одноэкранного UI.
- **KR-011 Вкладки и canvas routes.** Типизированные маршруты, вкладки,
  recent objects, deep link восстанавливает выбранный объект после перезапуска.
- **KR-012 Единый Markdown/KaTeX renderer.** Один безопасный renderer для
  чата, заметок, evidence и отчётов: math, code, таблицы, внутренние ссылки;
  опасный HTML/URL не исполняется. Локально упакованный KaTeX
  (рабочая гипотеза из `drafts/06` §8).
- **KR-014 Реестр tools/skills/plugins/hooks.** Контракты расширений,
  lifecycle, capability metadata; первый tool — чтение разрешённых файлов
  проекта; tool calls видны в event log.
- **KR-015 Политика разрешений.** Классификация read/write/network/compute/
  destructive; понятные подтверждения; scope разрешений не протекает.
- **KR-016 Видимый план, прогресс, стоп.** Активная задача, текущий шаг,
  tool calls, бюджет; stop оставляет согласованный commit и помечает
  незавершённый run.

Результат волны: срезы **R0 + R1** — устойчивый workspace и управляемый агент.
Каждая UI-карточка проходит app-tester + ui-reviewer (инфраструктура волны 0).

## 5. Волна 3 — первый сквозной research loop (этап C, R2)

Цель: главная ценность продукта. Пользователь формулирует brief, находит или
импортирует источник, проводит screening, создаёт evidence и claim и получает
версионированный синтез. Вертикальный срез P0 по `drafts/07` §3.

### ADR/spike перед кодом

1. **Первый набор search providers** (открытое решение №7): какие API
   (OpenAlex / Semantic Scholar / arXiv / Crossref), что доступно без ключей,
   fixture-provider как первый.
2. **PDF parser и OCR pipeline** (открытое решение №4): извлечение текста и
   постраничной структуры, детект сканов.

### Карточки

- **KR-020 Research Brief wizard.** Вопрос → редактируемый типизированный
  `ResearchBrief` (purpose, scope, языки, критерии, режим глубины, бюджет,
  stop conditions); ничего не начинается до подтверждения. Первое проявление
  принципа «важное из чата становится типизированным объектом».
- **KR-021 Agenda и state machine research run.** Кодовые состояния pilot →
  discovery → screening → reading → evidence → integration → coverage →
  synthesis с допустимыми переходами и resumability. LLM принимает
  семантические решения внутри границ, переходы контролирует код.
- **KR-022 Discovery provider interface.** Нормализованный интерфейс +
  fixture-provider: запрос, канал, параметры, сырой ответ, стоимость —
  всё детерминированно в provenance. Воспроизводимость важнее реального
  поиска на этом шаге.
- **KR-023 Candidate inbox.** Все кандидаты до screening с metadata, каналом
  и query provenance; никто не удаляется автоматически.
- **KR-024 ResearchObject + entity resolution.** DOI/arXiv/journal/supplement/
  code/dataset объединяются в один объект; сомнительный merge — предложение
  пользователю, не молчаливое решение.
- **KR-025 Импорт PDF.** Оригинал в artifact store, постраничный текст,
  качество извлечения; скан помечается «требует OCR», не считается прочитанным.
- **KR-026 Screening workflow.** Статусы include / exclude+reason / borderline /
  awaiting_fulltext / unavailable / duplicate с audit trail.
- **KR-027 Evidence Card.** Извлечение по схеме вопроса (method, conditions,
  sample, comparator, metric, result, uncertainty, limitations) с точной
  привязкой page/fragment: клик по evidence открывает место в источнике.
- **KR-028 Claims и связи.** Scoped claims, supporting/contradicting evidence,
  статусы proposed/supported/contested/superseded/retracted/unresolved;
  claim без evidence визуально помечается unsupported.
- **KR-029 Версионированный synthesis snapshot.** Связный Markdown-синтез из
  выбранного snapshot; каждое утверждение ведёт к evidence или помечено
  гипотезой; повторный синтез — новая версия с diff.

Результат волны: срез **R2** — CS test case проходит сквозной цикл
brief → источник → evidence → claim → синтез.

## 6. Волна 4 — knowledge workspace (этап D, R3)

Цель: knowledge graph становится редактируемой и проверяемой моделью знания,
а не побочным продуктом чата.

- **KR-030 Полная доменная схема.** Identity, versioning, provenance и
  relations для ResearchObject, Report, Concept, Evidence, Claim, Hypothesis,
  Gap, Experiment; fixtures на correction/retraction/conflicting evidence.
- **KR-031 Query API графа.** Nodes/edges поверх SQLite, traversal,
  neighbourhood, фильтры по snapshot/provenance; ответы на эталонные
  структурные вопросы («что опирается на один источник», «где противоречия»).
- **KR-032 Concept map и aliases.** Обратимые merge/split понятий, competing
  definitions остаются раздельными.
- **KR-033 Интерактивная graph view.** Локальный subgraph выбранного объекта
  (не весь граф разом), фильтры, синхронизация с canvas, performance dataset.
- **KR-034 Совместное редактирование.** Все предложения агента — diff с
  accept/reject/edit; reject не меняет граф, undo восстанавливает состояние.
- **KR-035 Hypothesis/Gap lifecycle.** Predictions, required evidence,
  falsification criteria; гипотеза не становится supported по тексту агента.
- **KR-036 Propagation corrections/retractions.** Retraction пересчитывает
  затронутые claims/hypotheses/synthesis как impacted с полным impact path.

Результат волны: срез **R3** (вместе с KR-050 timeline/diff из волны 5).

## 7. Волна 5 — эксперименты и долгая работа (этапы E, F; R4/R5)

Цель: гипотезы проверяются воспроизводимым кодом, а проект живёт месяцами.

### ADR/spike перед кодом

- **Packaged Python distribution и OS targets** (открытое решение №6) — до
  KR-083, но контракт sandbox (KR-040) можно проектировать сразу.

- **KR-040 Python sandbox contract.** Изолированный процесс: inputs/files/
  environment/limits/timeout/cancellation; запрет доступа вне scope.
- **KR-041 Experiment manifest.** Код, зависимости, seed, inputs, versions,
  limits, outputs; run повторяется из manifest с детерминированным результатом
  или явным diff окружения.
- **KR-042 Experiment view.** Manifest, код, логи, таблицы, графики,
  сравнение runs в canvas.
- **KR-043 Hypothesis → experiment → evidence.** Эксперимент закрывает
  конкретные obligations; finite result не превращается в универсальный claim.
- **KR-044 Экспорт HTML/PDF.** Общий pipeline рендеринга, экспорт фиксирует
  project snapshot.
- **KR-050 Timeline и сравнение snapshots**, **KR-051 Branches** с
  domain-aware merge, **KR-052 Episodic memory/trajectories**, **KR-053 Resume
  после перерыва** (из project state, не из chat history).
- **KR-054–056 (P2):** user memory со scope, semantic retrieval из knowledge
  state, procedural memory registry.
- **KR-057 (R&D):** consolidation/forgetting sandbox — ядро диссертационного
  test case, replay одной trajectory на разных memory policies.

## 8. Волна 6 — проверяемость и self-improvement (этапы G, H; R5/R6)

Цель: качество выводов защищено механизмами, а система начинает проверяемо
улучшать собственные стратегии.

- **KR-060 Многомерный quality profile источника** (без единого магического
  балла), **KR-061 Reviewer evidence extraction** (независимый review-pass
  критических карточек), **KR-062 Contradiction analysis** (genuine conflict /
  different scope / methodological disagreement), **KR-063 Coverage dashboard
  и audit** (без заявления абсолютной полноты), **KR-064 Stop recommendation**
  с причинами и uncertainty.
- **KR-065 (P2):** второй математический benchmark (canonical coin systems) —
  проверка, что система не привязана к LLM-memory domain и различает
  finite verification и общее доказательство.
- **KR-070–074 (P2):** полная telemetry trajectories → evals harness с
  baseline policies → reflection в ImprovementProposal → replay environment
  (детерминированный, на замороженных provider responses) → policy registry
  с promotion gates и rollback.
- **KR-075–077 (R&D):** learning-to-rank, contextual bandit в shadow mode,
  offline RL — только через evals и promotion gates, никогда напрямую в
  runtime.

## 11. Риски

1. **Миграция JSON → SQLite затягивается.** Смягчение: сделать её отдельным
   change с characterization-тестами текущего поведения до смены хранилища.
2. **Scope creep внутри карточек.** Смягчение: шаблон задания агенту из
   `drafts/07` §5 — не реализовывать соседние карточки, остановиться и
   спросить при новом продуктовом решении.
3. **Research loop (волна 3) — самый длинный срез.** Десять карточек;
   контрольная точка — KR-024 (inbox + entity resolution уже дают видимую
   ценность), не ждать KR-029 для демонстрации.
4. **Преждевременный learning.** Слои R&D (KR-057, 075–077) продвигаются
   только через evals; runtime обязан оставаться полностью работоспособным
   без learning layer (`drafts/01`, решение №16).
5. **UI-фичи без живой проверки.** Волна 0 — жёсткий блокер для волн 2, 4, 5;
   правило «renderer → app-tester + ui-reviewer» не отключается.
