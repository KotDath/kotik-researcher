# Delta spec: agent-orchestration

## Purpose

Разделение труда в SDD-цикле поверх openspec: primary-оркестратор ведёт
диалог и гейты, специализированные субагенты пишут спеки, код и ревью —
с границами доступа, grill-опросом пользователя и resume-семантикой.

## ADDED Requirements

### Requirement: Оркестратор как primary с запретом записи кода

Оркестратор SHALL быть primary-агентом (точка входа пользователя) и MUST НЕ
править `src/**` и `src-tauri/**` — запрет SHALL быть структурным (permission
в определении агента), не дисциплинарным. Оркестратор ведёт роутинг, брифует
субагентов, показывает артефакты пользователю, проводит approve-гейты и
архивацию через openspec CLI.

#### Scenario: Оркестратор пытается править код

- **WHEN** оркестратор получает задачу, требующую правки `src/**`
- **THEN** правка блокируется permission'ом, а задача делегируется implementer'у

#### Scenario: Пользователь вызывает /opsx:propose в оркестраторе

- **WHEN** пользователь вызывает `/opsx:propose`, находясь в агенте-оркестраторе
- **THEN** оркестратор создаёт change через openspec CLI (плюс vision.md при
  наличии explore-контекста) и делегирует написание артефактов spec-writer'у,
  который сам подгружает скилл openspec-propose через skill tool

#### Scenario: Пользователь вызывает /opsx:apply в оркестраторе

- **WHEN** пользователь вызывает `/opsx:apply` для одобренного change
- **THEN** оркестратор делегирует реализацию implementer'у по routing card,
  а тот подгружает скилл openspec-apply-change через skill tool

#### Scenario: Пользователь вызывает /opsx:archive в оркестраторе

- **WHEN** пользователь вызывает `/opsx:archive` для завершённого change
- **THEN** оркестратор выполняет архивацию сам (sync спек, validate, перенос
  в archive через openspec CLI)

#### Scenario: Мелочь без change

- **WHEN** пользователь просит ответ на вопрос или правку, не требующую change
- **THEN** оркестратор отвечает сам, без создания change и без делегирования

### Requirement: Grill-гейт spec-writer'а

Написание артефактов change SHALL делегироваться spec-writer'у. Spec-writer
SHALL провести опрос пользователя напрямую (question tool) итеративными
раундами по карте покрытия: скоуп и границы, критерии приёмки как наблюдаемые
свойства, non-goals, граничные случаи, состояния UX, режимы отказа. Артефакты
MUST НЕ создаваться, пока открыты вопросы, влияющие на объём или критерии
приёмки. Правки спеки SHALL выполняться возобновлением той же сессии
spec-writer'а (task_id).

#### Scenario: Опрос перед артефактами

- **WHEN** оркестратор делегирует создание change spec-writer'у
- **THEN** spec-writer начинает с раундов вопросов пользователю, а не с
  генерации файлов

#### Scenario: Правки после review packet

- **WHEN** пользователь вносит коррекцию в показанную спеку
- **THEN** коррекция передаётся в ту же сессию spec-writer'а (resume по
  task_id), и пользователю показывается актуальный review packet повторно

#### Scenario: Недоступен question tool (fallback)

- **WHEN** smoke-тест или работа показывают, что question tool субагенту
  недоступен в текущей версии opencode
- **THEN** grill ведёт оркестратор, а spec-writer оформляет согласованное в
  артефакты (fallback задокументирован в процедуре)

### Requirement: Стык explore → спека через vision.md

Существенные результаты explore (факты, замеры, сравнения, отвергнутые
варианты) SHALL фиксироваться в `vision.md` в папке change до делегирования
spec-writer'у. Брифы субагентам SHALL ссылаться на файлы на диске и включать
дословно: что согласовано, что отвергнуто и почему, контракт возврата.
Отвергнутое в vision.md MUST НЕ пересматриваться без новых фактов.

#### Scenario: Change после explore-диалога

- **WHEN** change создаётся по итогам explore-сессии
- **THEN** оркестратор сначала пишет vision.md с дистиллятом, и бриф
  spec-writer'у указывает на него как обязательное чтение

#### Scenario: Мелкий change без explore

- **WHEN** change создаётся без предшествующего explore
- **THEN** vision.md не требуется, контекст передаётся брифом дословно

### Requirement: Routing card и выбор implementer'а

При создании change оркестратор SHALL зафиксировать в proposal мини routing
card: Profile (feature/bugfix/refactor), Size, Risk, Implementation
(standard|deep) с сигналами. Реализация SHALL делегироваться implementer'у
(быстрая модель) при `standard` и implementer-deep (сильная модель) при
`deep`. Значение Implementation MUST НЕ пересматриваться implementer'ом
во время реализации.

#### Scenario: Выбор по routing card

- **WHEN** спека одобрена с `Implementation: deep`
- **THEN** реализация делегируется implementer-deep, а не implementer'у

#### Scenario: Попытка переключения в процессе

- **WHEN** implementer сталкивается со сложностью выше ожиданий
- **THEN** он возвращает блокер оркестратору, а не продолжает «вглубь»;
  решение о смене режима принимает оркестратор с пользователем

### Requirement: Ревью-гейт кода

Реализация change SHALL проходить код-ревью субагентом reviewer'ом против
спеки. Reviewer SHALL вернуть вердикт `APPROVE` или `CHANGES_REQUESTED` с
воспроизводимыми evidence по каждой находке. Находки `CHANGES_REQUESTED`
исправляет тот же implementer (resume по task_id); цикл исправлений MUST
быть ограничен тремя итерациями, далее — эскалация пользователю.

#### Scenario: Ревью без замечаний

- **WHEN** реализация завершена и DoD зелёный
- **THEN** reviewer получает бриф (спека + дифф) и возвращает явный вердикт

#### Scenario: Цикл исправлений

- **WHEN** reviewer вернул `CHANGES_REQUESTED`
- **THEN** находки передаются тому же implementer'у (resume), после исправлений
  ревью повторяется; после третьей итерации без APPROVE — решение пользователя

### Requirement: Вложенный technical-consultant

Implementer SHALL иметь возможность делегировать локальный сложный вопрос
technical-consultant'у напрямую (вложенный task), без ретрансляции через
оркестратора. Другие субагенты MUST НЕ иметь права вызывать кого-либо, кроме
явно разрешённого (для implementer'а — technical-consultant и explore).

#### Scenario: Локальный затык

- **WHEN** implementer после разведки кода упёрся в точечный сложный вопрос
- **THEN** он вызывает technical-consultant с инвариантом, фактическим
  поведением и конкретным вопросом — оркестратор не участвует

### Requirement: Границы доступа ролей

Границы SHALL быть структурными (permissions в определениях агентов):
spec-writer правит только `openspec/**`; implementer и implementer-deep
правят `src/**`, `src-tauri/**` и папку текущего change; reviewer и
technical-consultant — read-only; вызов субагентов ограничен явным списком
на роль.

#### Scenario: Spec-writer пытается править код

- **WHEN** spec-writer пытается изменить файл в `src/**`
- **THEN** правка блокируется permission'ом

### Requirement: Explore — режим, не гейт

Explore-диалог SHALL оставаться режимом оркестратора и MUST НЕ быть
обязательной стадией перед change. Делегированию подлежат структурированные
активности (grill, артефакты, реализация, ревью); неструктурированное
мышление с пользователем MUST НЕ делегироваться. Механическая разведка
кодовой базы MAY делегироваться встроенному explore-субагенту.

#### Scenario: Мышление без change

- **WHEN** пользователь хочет обсудить идею без создания change
- **THEN** оркестратор ведёт explore-диалог сам, не создавая артефактов и
  не делегируя диалог субагенту
