# vision.md — add-orchestrator (дистиллят explore-сессии)

Источник: explore-диалог 2026-08-16 (сессия после ретроспективы add-ratatui-tui).
Это вход для spec-writer'а: факты проверены в диалоге, отвергнутое не
пересматривать без новых фактов.

## Зачем (боль)

- Ретроспектива сессии add-ratatui-tui: один агент прошёл propose→apply→
  archive→push монолитно (~5M токенов, ~270 мин). Нет разделения труда.
- Перед спекой было задано 2 вопроса — пользователь ожидает grill-опрос
  на feature-изменениях (пожелание «что-то в духе grill-me»).
- Ревью кода отсутствует как этап; пользователь считает его неотъемлемой
  частью реализации фичи.

## Факты (проверено в explore)

1. **Question tool доступен кастомным субагентам** с `question: allow` в
   frontmatter — проверено пользователем на backup-ветке. Встроенный
   `general` его НЕ имеет (эксперимент в сессии). В текущей сессии
   проверить нельзя: реестр агентов task tool фиксируется на старте.
   → первая задача change: smoke-тест.
2. **Backup-ветка** (`git show backup:...`) — работавший прототип
   оркестрации: primary-orchestrator с `src/ deny`, ~25 субагентов,
   routing card, ideator с vision-интервью (раунды 3–5 вопросов, карта
   покрытия), брифинг-контракт («как коллеге, вошедшему в комнату»),
   resume по task_id, вердикты SPEC_READY/NEEDS_*, APPROVE/
   CHANGES_REQUESTED, цикл фиксов ≤3 итераций, agent-sessions.md.
   Слабость backup: state machine спек была ручной (Status в proposal.md,
   архивация руками агента) — теперь это закрывает openspec CLI.
3. **openspec explore — не стадия перед propose**, а стойка «before or
   during a change». Обязательность explore для фич — наша надстройка в
   AGENTS.md. Ванильный propose имеет свой шаг кларификации.
4. **openspec update перезаписывает** сгенерированные скиллы/команды
   (помечены `generatedBy`). Официальные слоты кастомизации: config.yaml
   (context, rules per artifact, guidance для apply/archive). Слота для
   поведения фазы propose нет.
5. **herdr доступен** (мы внутри него, HERDR_ENV=1): мультиплексор
   терминалов, умеет запускать агентов в панелях, читать их состояние.
6. Модели в текущем конфиге: primary k3, есть opencode-go/deepseek-v4-flash
   (reflector). Наличие pro-моделей — инвентаризировать при реализации.

## Решено (не пересматривать без новых фактов)

- **Транспорт — opencode subagents, не herdr.** Herdr отвергнут как
  транспорт оркестрации: теряются контракты возврата, permission-границы
  в frontmatter, pinned-модели, attribution в usage/digest (дочерние
  сессии), а чтение результата с alternate screen TUI ненадёжно. Herdr
  остаётся опциональным слоем наблюдения, в процедуру не входит.
- **Логика оркестрации живёт в `.opencode/agents/*.md`**, ванильные
  `/opsx:*` не патчим (perеживает openspec update, одна точка кастомизации).
- **Состав ролей (от пользователя, дословно)**: оркестратор; чел, пишущий
  спеки и задающий кучу вопросов (правки — resume той же сессии); чел,
  пишущий код на быстрой модели; чел, проводящий ревью кода;
  чел-консультант для вопросов кодера; чел, пишущий код на сложной модели,
  если фича сложная (решение фиксируется на этапе спеки).
- **Grill ведёт spec-writer** (не оркестратор) — ожидание пользователя.
- **Explore-субагент не нужен**: делегируется структурированное (grill,
  артефакты, код, ревью), не делегируется неструктурированное (explore-
  диалог — режим оркестратора; механическая разведка кода — встроенный
  explore субагент).
- **Стык explore → спека**: vision.md на диске в папке change (этот файл —
  первый экземпляр), бриф spec-writer'у ссылается на файлы, не пересказ.
- **Гейта три**: grill (spec-writer), approve спеки (пользователь),
  reviewer (код). Explore гейтом не является.
- **Routing card мини**: Size / Risk / Implementation(standard|deep);
  Implementation фиксируется в proposal на этапе спеки и не
  пересматривается implementer'ом.
- **Из backup НЕ забираем**: консилиум, app-tester, ui-reviewer,
  fast/deep-сплит spec-writer'а, зоопарк ~25 ролей, agent-sessions.md.
- **Reviewer ≠ модель оркестратора** по возможности (anchor bias);
  кандидаты уточнятся инвентаризацией провайдеров.
